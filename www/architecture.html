The shape of the program

One process. Multi-threaded. One main thread that accepts connections and dispatches them. Eight worker threads that handle requests in parallel. A bounded queue between them holding pending work.

The lifecycle of one request

Startup. The server creates a TCP socket, binds it to port 8080, calls listen(), initializes the task queue, and spawns eight worker threads. Each worker immediately blocks on the queue's "not empty" condition variable. The main thread enters the accept loop.

Connection arrives. A client sends a TCP SYN. The kernel completes the three-way handshake and parks the resulting connection in the listen backlog. The main thread, blocked in accept(), wakes up and gets a new file descriptor.

Dispatch. The main thread submits the file descriptor to the queue (locks mutex, writes to ring buffer, signals "not empty", unlocks) and immediately loops back to accept(). One of the sleeping workers is woken by the signal.

Handling. The woken worker dequeues the file descriptor and calls handle_client. That function reads the HTTP request, parses the request line with sscanf, checks that the method is GET, builds the filesystem path, and calls serve_file. serve_file opens the file, builds the response headers (status line, Content-Type, Content-Length, Connection), writes them to the socket, then streams the file body in 4 KB chunks.

Cleanup. The worker closes the client socket, which triggers a TCP FIN. The worker loops back to queue_dequeue and either picks up another pending request or goes back to sleep.

What's shared between threads

Almost nothing. The only shared mutable state is the task queue, which is protected by its mutex. Every other piece of state — the request buffer, parsed fields, file descriptors during handling — is per-thread stack memory. The helper functions handle_client, parse_request_line, send_error, and serve_file have no shared state and require no synchronization. Multiple instances run concurrently on different threads without interfering.

Why this design

The alternative concurrency models considered:

Thread-per-connection. Create a new thread for every accepted connection. Simple but expensive: thread creation involves a kernel call, a stack allocation, and scheduler overhead. Under load (10,000 connections per second) it collapses.

Fork-per-connection. Same idea but with processes. Provides isolation but is even more expensive than threads. Apache used this in its early days; modern servers don't.

Thread pool (chosen). Fixed number of workers, created at startup. Connections are handed to whichever worker is free. Bounded resource usage, no per-request startup cost, simple to reason about. The pragmatic choice for moderate load.

Event loop with epoll/kqueue. One thread can handle thousands of connections by multiplexing I/O. Most efficient, also the most complex. This is what nginx and Node.js use. A possible future direction for this project.

Known limitations

The server is deliberately minimal. It does not yet implement:

  • HTTP/1.1 keep-alive (each request opens a new TCP connection)
  • Chunked transfer encoding
  • TLS / HTTPS
  • Request size limits beyond the 4 KB initial buffer
  • Conditional requests (If-Modified-Since, ETags)
  • Compression (gzip, brotli)

All of these are reasonable next steps but were out of scope for the initial implementation.
